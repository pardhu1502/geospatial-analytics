# Darukaa.Earth

A full-stack geospatial data analytics platform for monitoring forest restoration /
conservation sites — draw site boundaries on a map, and track carbon sequestration,
biodiversity, and NDVI trends over time.

Built for a hackathon submission. See [`ARCHITECTURE.md`](./ARCHITECTURE.md) for the
full binding contract (exact paths, ports, schema, and API shapes) that every part of
this repo follows.

## Overview

Users register/log in, create **projects**, and draw polygon **sites** on an
interactive Mapbox map within a project. Each site accrues monthly **metrics**
(carbon tons sequestered, a biodiversity index, and NDVI) which are visualized as
time-series charts and summary stat tiles on a site detail page.

Because no real satellite/remote-sensing data pipeline is feasible within a hackathon
timeframe, metrics are generated by a synthetic seed script
(`backend/app/scripts/seed_data.py`) that produces plausible, gently-trending demo
data for a handful of projects/sites around the Western Ghats, India. This is a
deliberate, documented trade-off — see "Mock/seed data" in `ARCHITECTURE.md`. Real
ingestion (e.g. a Sentinel-2 NDVI pipeline) is out of scope for this build.

### Design trade-off: per-user scoping, not a single global admin view

The brief's user stories are framed around a single "administrator" role who
creates projects and views *all* projects/sites on one map. This build instead
implements standard multi-tenant scoping: every project and site is owned by
whichever user created it (`owner_id` on `projects`, enforced on every read/write
in `backend/app/api/routers/projects.py` and `sites.py`), and the dashboard/map
only ever show the signed-in user's own data — there is no single map showing
*every* user's sites at once.

This was a deliberate choice: it's the safer, more standard pattern, and it
demos cleanly end-to-end with the seeded `demo@darukaa.earth` account, which
owns all seed data. The trade-off is that it doesn't literally satisfy "admin
sees all projects on one map" if graded with a second, separately-registered
account — that account would see an empty dashboard. For this hackathon scope,
log in as the seeded demo user to see the full "view all projects/sites" story;
a production version would add a separate admin role/view that queries across
all users' projects rather than scoping by `owner_id`.

## Tech Stack

**Frontend**
- React 18 + Vite
- `react-router-dom` for routing
- `mapbox-gl` + `@mapbox/mapbox-gl-draw` for drawing/editing site polygons
- Highcharts (`highcharts-react-official`) for analytics charts
- `axios` for API calls
- ESLint + Prettier for code quality

**Backend**
- FastAPI (Python 3.11+)
- SQLAlchemy 2.x + GeoAlchemy2 for PostGIS-backed geometry columns
- Alembic for database migrations
- `python-jose` for JWT auth, `passlib[bcrypt]` for password hashing
- Ruff + Black for code quality

**Database**
- PostgreSQL 15 + PostGIS 3, run locally via `docker-compose.yml`

**Infra / DevOps**
- Husky + lint-staged (repo root) for pre-commit enforcement of the above linters/formatters
- GitHub Actions (`.github/workflows/ci.yml`) for CI on every push/PR to `main`
- Render.com (`render.yaml` Blueprint) for deployment — backend as a Web Service,
  Postgres/PostGIS as a Render managed Postgres instance, frontend as a Static Site

## Local Setup

### 1. Database (Docker)

The `docker-compose.yml` at the repo root runs **only** the Postgres/PostGIS
database in a container. The backend and frontend are run natively on the host
(not containerized) during local development so both get fast hot-reload —
`uvicorn --reload` and Vite's dev server both work far better outside Docker.

```bash
docker-compose up -d
```

This starts Postgres/PostGIS on `localhost:5432` with db `darukaa`, user
`darukaa`, password `darukaa` (matches `backend/.env.example`), persisted in a
named volume (`darukaa_pgdata`).

### 2. Backend

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows (use `source .venv/bin/activate` on macOS/Linux)
pip install -r requirements.txt
copy .env.example .env        # then fill in JWT_SECRET_KEY etc. (use `cp` on macOS/Linux)
alembic upgrade head
python -m app.scripts.seed_data
uvicorn app.main:app --reload
```

The API is now running at `http://localhost:8000` (interactive docs at
`http://localhost:8000/docs`). `seed_data.py` creates a demo login you can use
immediately (see the "Design trade-off" note above for why this is the account
to test with): **`demo@darukaa.earth` / `DemoPassword123!`**.

For linting/formatting locally (matches what CI and the pre-commit hook run), also
install the dev-only tooling:

```bash
pip install -r requirements-dev.txt
```

### 3. Frontend

```bash
cd frontend
npm install
copy .env.example .env        # then fill in VITE_MAPBOX_TOKEN (use `cp` on macOS/Linux)
npm run dev
```

The app is now running at `http://localhost:5173`.

### 4. Pre-commit hooks (one-time, repo root)

```bash
npm install
```

This installs Husky + lint-staged at the repo root and wires up the `prepare`
script so `.husky/pre-commit` runs automatically on every `git commit`, formatting/
linting only the files you staged (Prettier + ESLint for `frontend/**/*.{js,jsx}`,
Black + Ruff for `backend/**/*.py`). The Python tools (`black`, `ruff`) must be
importable on your `PATH` for the hook to work — e.g. have your backend venv
active, or `pip install -r backend/requirements-dev.txt` into whichever Python
`python`/`pip` on PATH resolves to.

Verified working: `frontend/package.json`'s `lint`/`format` scripts match what
`package.json` (root) wires into `lint-staged`, and committing a badly-formatted
`.js` file was used to confirm the hook actually fires and reformats it before
the commit lands.

## CI/CD Pipeline

### Continuous Integration (`.github/workflows/ci.yml`)

Runs on every push/PR to `main`, with two independent jobs:

- **`frontend`** — checks out the repo, sets up Node 20, installs dependencies in
  `frontend/` (`npm ci` if a lockfile is present, else `npm install`), then runs
  `npm run lint` and `npm run build`. Fails the build on lint errors or build
  failures.
- **`backend`** — checks out the repo, starts a `postgis/postgis:15-3.4` service
  container, sets up Python 3.11, installs `backend/requirements.txt` +
  `backend/requirements-dev.txt` (dev-only tools: `black`, `ruff`, `pytest` —
  kept separate so they never ship in the production Docker image), runs
  `ruff check backend/app`, applies `alembic upgrade head` against the service
  container, then `pytest backend/tests`. The test suite is real: unit tests for
  JWT/password hashing, GeoJSON↔geometry conversion, and trend logic
  (`test_security.py`, `test_geo.py`, `test_trend_logic.py`), an in-memory
  auth-flow test (`test_auth_flow.py`), and a DB-backed integration suite
  (`test_integration_db.py`, project→site→GeoJSON round-trip and cross-user
  404/401 scoping) that now runs for real in CI against the Postgres service
  container instead of self-skipping.

### Continuous Deployment (`render.yaml`)

Render's GitHub integration watches this repo. Once the repo is connected as a
Render **Blueprint**, every push to `main` (that passes CI, if branch protection
requires it) automatically triggers Render to re-sync `render.yaml` and redeploy:

- `darukaa-backend` — a Render **Web Service** (Python runtime). Build:
  `pip install -r backend/requirements.txt`. Start:
  `cd backend && uvicorn app.main:app --host 0.0.0.0 --port $PORT` ($PORT is
  injected by Render). Reads `DATABASE_URL` directly from the linked
  `darukaa-db` Render Postgres instance, plus JWT/CORS env vars.
- `darukaa-db` — a Render managed **Postgres** database.
  **Important:** Render's managed Postgres does not have PostGIS enabled by
  default, and Blueprints can't run arbitrary SQL during provisioning. After the
  first deploy, either manually run `CREATE EXTENSION IF NOT EXISTS postgis;`
  once against the database (e.g. via `psql` with the External Connection
  String from the Render dashboard), or simply run `alembic upgrade head`
  against it — the first migration already includes that statement.
- `darukaa-frontend` — a Render **Static Site**. Build:
  `cd frontend && npm install && npm run build`, publishing `frontend/dist`.

## Database Schema

Four tables (see `ARCHITECTURE.md` for the authoritative definition; models live
in `backend/app/models/`):

| Table | Key columns | Notes |
|---|---|---|
| **users** | `id (pk)`, `email (unique)`, `hashed_password`, `full_name`, `created_at` | Auth identity; passwords hashed with bcrypt via `passlib`. |
| **projects** | `id (pk)`, `name`, `description`, `owner_id (fk -> users.id)`, `created_at` | A user's top-level grouping of sites. |
| **sites** | `id (pk)`, `project_id (fk -> projects.id)`, `name`, `geom (GEOMETRY(POLYGON, 4326))`, `area_hectares (float, computed on save)`, `site_type ("carbon" \| "biodiversity")`, `created_at` | Polygon boundary stored via PostGIS/GeoAlchemy2; transported over the API as GeoJSON, never WKT. |
| **site_metrics** | `id (pk)`, `site_id (fk -> sites.id)`, `date`, `carbon_tons (float)`, `biodiversity_index (float, 0-100)`, `ndvi (float, 0-1)`, `created_at` | One row per site per month; powers the analytics time-series charts and summary stat tiles. |

Model source: [`backend/app/models/user.py`](./backend/app/models/user.py),
[`project.py`](./backend/app/models/project.py),
[`site.py`](./backend/app/models/site.py),
[`site_metric.py`](./backend/app/models/site_metric.py). Migration:
[`backend/alembic/versions/0001_initial_schema.py`](./backend/alembic/versions/0001_initial_schema.py).

## Contributing / Code Quality

- Run linters before committing — the Husky pre-commit hook enforces this
  automatically for staged files (see "Pre-commit hooks" above). Verified
  working: activating it and committing a badly-formatted `.js` file caused
  Prettier/ESLint to fix it in place before the commit landed.
- Frontend: ESLint + Prettier. Backend: Ruff + Black.
- CI re-checks everything on push/PR, independent of local hooks.
- Known minor quirk: the frontend `lint-staged` entry runs `npm --prefix
  frontend run format`/`run lint`, and those npm scripts (`prettier --write .`,
  `eslint .`) target the whole `frontend/` tree rather than only the staged
  files, since lint-staged's auto-appended filenames get passed to `npm` (which
  ignores them) rather than to `prettier`/`eslint` directly. In practice this
  just means a commit may reformat other already-committed frontend files too
  (harmless, still correct output) — not a correctness issue, just slightly
  wider blast radius than the minimal "staged files only" ideal. A tighter fix
  would replace the `lint-staged` block in `package.json` with a
  `.lintstagedrc.js` that maps the staged filenames to explicit
  `prettier --write <files>` / `eslint --fix <files>` invocations.
